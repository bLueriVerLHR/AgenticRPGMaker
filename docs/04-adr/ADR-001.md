# ADR-001 — Shared Engine Core: Component-Based Entities, Scene Graph, Event Bus (packages/core)

## Metadata

- **Status:** proposed
- **Date:** 2026-08-25
- **Author:** Design-B (Architecture Design member)

## Status

- **Status:** proposed
- **Supersedes:** none

## Context

The project ships **two browser-based consumers** of the same game content:

1. the **editor** (React + TypeScript + Vite, per D13) — places tiles, defines
   events, previews maps;
2. the **runtime** (framework-free vanilla TS, per D13) — plays the game in a
   portable `www` folder on **any static host and JoiPlay-type mobile HTML
   runtimes** (Q1/RQ1).

The strongest risk in this split is that editor and runtime **diverge into two
engines**: each would interpret maps, events, and saves slightly differently,
breaking round-trips (edit → play → edit), duplicating bug fixes, and doubling the
maintenance surface. The data model and the event interpreter must therefore be a
**single source of truth** shared by both.

Constraints that force the shape of the core:

- **Portability (Q1/RQ1/D13):** the runtime must run on JoiPlay WebViews and any
  static host → **no framework dependencies** (no React, no Vue, no PixiJS) in the
  runtime path. Whatever the core is, it must be framework-free vanilla TS.
- **Scripting (Q4):** game logic is TypeScript + an **event system** + script/API;
  the same event interpreter must behave identically in the editor's preview and in
  the runtime, otherwise authors see one result in the editor and another in the
  game.
- **MVP sync (D16):** world-state sync is an MVP limitation; the event interpreter
  is client-side, so there is no server-side twin to keep in sync in the MVP — but
  the interpreter's correctness is still load-bearing.
- **Repo shape (D15):** a `packages/core` package exists and is consumed by
  `packages/runtime` and `packages/editor` via pnpm workspaces.
- **Tests (03-wal-process.md §3):** unit tests are mandatory before any merge or
  real-environment run; a pure-logic core is the natural unit-test target.

## Decision

All shared engine logic lives in **one framework-free, vanilla-TypeScript package:
`packages/core`**, built around three pillars:

1. **Component-based entities.** A `GameObject` is a lightweight container of
   `Component`s (`Transform`, `Sprite`, `Collider`, `EventInterpreter`,
   `Behavior`, …). Components own data and behavior; the engine and game code
   compose entities from components. No deep inheritance hierarchies — the core
   provides composition, iteration, and lookup (by id / by component type).
2. **A scene graph.** Entities are arranged in a tree (parent/child transforms,
   layer ordering, culling groups). The scene graph is the runtime's source of
   truth for "what is in this map right now" and is driven by the map data model
   (see ADR-003).
3. **An event bus.** Components and engine subsystems communicate through a typed
   event bus (`emit`/`on`), including gameplay events (walk, collide, dialogue,
   switch/variable changes). The **event interpreter** — the component that runs
   event pages and their commands/conditions (ADR-003) — is part of the core and is
   shared verbatim by editor preview and runtime.

**Both the editor and the runtime consume this same core.** The editor uses it for
map preview/playtest and for serializing/deserializing project data; the runtime
uses it for the actual game loop. Neither implements its own data model or event
interpreter. The core is intentionally **dependency-free** (no DOM, no WebGL, no
frameworks — pure data + logic) so it runs identically in browser, JoiPlay, and
Node (tests).

## Consequences

### Positive

- **One data model.** Maps/events/saves are defined and validated once (ADR-003);
  editor and runtime cannot drift apart.
- **One event interpreter.** Preview in the editor is behaviorally identical to the
  shipped game — a core correctness guarantee for authors.
- **Portable.** Pure vanilla TS, no runtime dependencies → runs on any browser,
  JoiPlay, and static hosts without bundling surprises; a plain `tsc` build is
  enough for the runtime path.
- **Testable.** Core logic tests (Vitest, per D15) run in Node with no DOM/GL
  mocking; this satisfies the mandatory-testing rule cheaply.
- **Reusable for future consumers.** The C++ server, a future authoritative server
  (Q2), or headless test harnesses can load the same core logic.
- **Pattern home.** Pluggable behavior (Strategy pattern for the future LLM-NPC
  interface, Q4) and the renderer facade (ADR-002) slot cleanly around a stable
  core.

### Negative

- **Core must stay dependency-free.** Any tempting npm dependency is either
  rejected or pushed into a shell layer; the one documented exception is the
  schema-validation library chosen in ADR-003 (to be confirmed at review — see
  ADR-003, which flags this tension explicitly).
- **API stability burden.** Because two packages depend on core, breaking changes
  require coordinated migration; core needs a semantic-versioning policy, a
  deprecation path, and clear changelog discipline.
- **Indirection cost.** Simple operations (e.g. reading a variable, toggling a
  switch) go through the core API instead of direct editor state — a small amount
  of ceremony for a large consistency win.
- **Component composition learning curve.** Team members used to classic
  class-inheritance engines must learn the component idiom; mitigated by keeping
  the core's public surface small and documented.
