# ADR-002 — Renderer Interface: WebGL Default with Automatic Canvas2D Fallback

## Metadata

- **Status:** proposed
- **Date:** 2026-08-25
- **Author:** Design-B (Architecture Design member)

## Status

- **Status:** proposed
- **Supersedes:** none

## Context

Rendering was decided in **Q3** (Round 1): a **WebGL-based renderer interface**
with **upper layers built on the interface**, and **heavy use of design patterns**
to isolate risk. **RQ2** (Round 2) added the distribution requirement: **JoiPlay
WebViews and weak devices may have poor or no WebGL**, so we need **capability
detection and an automatic Canvas2D fallback renderer sharing the same upper
layers**.

Additional constraints:

- The runtime must stay **framework-free vanilla TS** (D13) — PixiJS and other
  renderer libraries are rejected, per Q3's chosen option (a): renderer interface,
  from-scratch implementations.
- The renderer lives in its own package `packages/renderer` (D15), consumed by the
  runtime; the editor preview reuses the same renderer via the shared core
  (ADR-001) so preview and game look identical.
- The scene graph and gameplay code in `packages/core` (ADR-001) must never
  reference a concrete backend — they draw through the interface only.
- Mandatory testing (03-wal-process §3) and structured logging (§2) apply to the
  renderer as to everything else.

## Decision

Define a **Renderer interface** in `packages/renderer` that is the *only* surface
upper layers may call. Two implementations of it:

- **WebGLRenderer** — the **default** (tries WebGL2, falls back to WebGL1);
- **Canvas2DRenderer** — an **automatic fallback** used when no WebGL context can
  be created.

At startup the runtime (via a small **capability-detection module**) probes for a
WebGL context and instantiates the appropriate implementation with a simple
**factory**. The chosen backend is **logged at `info` level** (per logging rules)
so support issues are diagnosable from logs alone.

### Interface surface (methods)

The interface exposes:

- **Frame control:** `beginFrame()`, `endFrame()`
- **Drawing primitives:** `drawTile(tile, x, y, opts)`, `drawSprite(textureId,
  frame, x, y, opts)`, `drawText(text, x, y, opts)`, `drawRect(x, y, w, h, fill,
  stroke)`
- **Camera / transform:** `setCamera(viewport, zoom)`, `pushTransform(t)`,
  `popTransform()` (the scene graph in core passes world transforms through these)
- **Resources:** a `TextureManager` (a sibling interface, injected) that loads
  images, builds atlases, caches textures, and hands back opaque texture ids —
  backends translate ids to their own GPU/Canvas resources.

### Implementation notes

**WebGL default (WebGLRenderer)**
- **2D sprite batching:** sprites are collected per frame into a dynamic vertex
  buffer (interleaved position / UV / color), batched into as few draw calls as
  possible; the batch flushes automatically on texture change or at `endFrame()`.
  A texture atlas keeps most sprites/tiles on one texture to minimize state
  switches.
- **Tilemap rendering:** tile layers are drawn per-layer as quad meshes built from
  the map's tile indices (ADR-003); only visible tiles (viewport culling) are
  emitted to the batch.
- **Minimal shaders:** one textured-quad vertex+ fragment shader pair (position,
  uv, tint/alpha); no post-processing, shadow, or lighting shaders in MVP. Shader
  programs and uniform locations are cached.

**Canvas2D fallback (Canvas2DRenderer)**
- Same interface, implemented with the 2D context: `drawTile`/`drawSprite` →
  `drawImage` with source-rect (from the same `TextureManager` atlas),
  `drawText` → `fillText` with the same font configuration, `drawRect` →
  `fillRect`/`strokeRect`, camera/transform → `ctx.save()`/`translate`/`scale`/
  `restore()` (or `setTransform`).
- Batching is a no-op here (immediate mode): correctness first, optimization
  possible later without touching upper layers.
- Canvas2D doubles as a debug cross-check for GL correctness in tests (golden
  comparisons / a `software-render` debug flag).

**Capability detection order:** WebGL2 → WebGL1 → Canvas2D; log the chosen backend
at `info`, and surface it in the About/debug UI.

**Context-loss handling:** the WebGL renderer listens for `webglcontextlost` /
`webglcontextrestored` and re-creates GPU resources; on unrecoverable loss it
re-runs capability detection and can hot-swap to Canvas2D.

## Consequences

### Positive

- **One API, two backends.** Upper layers (core scene graph, gameplay code, editor
  preview) are backend-agnostic; adding a future backend (e.g. a headless/null
  renderer for tests) is additive.
- **Portability.** JoiPlay and weak devices still render (degraded but functional)
  instead of failing; desktop browsers get the fast WebGL path automatically with
  zero user configuration.
- **Risk isolation via design patterns** (Q3): Strategy for backend selection,
  Factory for implementation creation, Facade over WebGL complexity — the risky
  WebGL code is contained behind the interface.
- **Testing leverage.** The Canvas2D implementation provides a fully software,
  deterministic path that can run in CI/Vitest without a GPU; the null renderer can
  be used for pure-logic tests.
- **Fallback = debugging aid.** Problems can be diffed between backends to decide
  whether a bug is in GL code or in scene logic.

### Negative

- **Two code paths to maintain and test.** Behavior drift between WebGL and
  Canvas2D is a real risk; mitigated by backend-comparison tests and keeping the
  interface small.
- **Some effects are WebGL-only.** Shaders, per-sprite tint/glow, and large
  particle counts may be unavailable or disabled on Canvas2D — this is a
  **documented degradation** (a feature-capability table the runtime exposes and
  logs), not a silent difference.
- **WebGL context management cost.** Context loss/restore, shader compilation, and
  buffer management add non-trivial complexity to the default path.
- **Batching complexity in MVP.** Sprite batching is real work before prettiness;
  must be scheduled explicitly and not half-built. (Alternative considered: ship
  the Canvas2D renderer first and WebGL second — rejected because WebGL is the
  default target device path, and the interface contract must be proven by the
  real implementation.)
