# ADR-003 — Versioned JSON Data Formats (Shared TS Types + Validation in packages/core)

## Metadata

- **Status:** proposed
- **Date:** 2026-08-25
- **Author:** Design-B (Architecture Design member)

## Status

- **Status:** proposed
- **Supersedes:** none

## Context

The editor and the runtime must read and write **identical data** — maps, tilesets,
saves, and editor projects — or the round-trip breaks (edit → play → edit) and the
single-source-of-truth promise of ADR-001 collapses. **D14** decided the approach:
**versioned JSON schemas backed by shared TS types** for maps / events / saves /
protocol.

Constraints and precedents that shape this ADR:

- **Shared types live in `packages/core`** (D15, ADR-001) so both editor and runtime
  validate against the exact same definitions — no parallel type declarations that
  can drift.
- **Saves are portable** (RQ1): IndexedDB in the browser, optional C++ local-file
  saves — a save file is a JSON document that must be valid in both worlds.
- **Future-proofing:** later we may add **binary or compressed** storage (bigger
  maps, faster load). A top-level **schema-version field** ensures those formats
  never silently break v1 consumers; a reader must know, before parsing anything
  else, which schema it is looking at.
- **Validation is mandatory** (03-wal-process §3): runtime validation at load time
  plus **schema tests** so a schema change is impossible without its tests passing.
- The validation library must run in browser + Node (tests) and be framework-free
  in the runtime path (D13) — narrowing the field of candidates.

## Decision

All game data formats are **versioned JSON**, validated by **shared TS types** plus
a **validation library**, both living in **`packages/core`**. The recommended
validation library is **[zod](https://github.com/colinhacks/zod)** — **choice to be
confirmed by the leader** at review (zod gives: TS type inference straight from the
schema, so the schema *is* the type; runtime validation in both browser and Node;
zero framework dependency, so it is compatible with the framework-free runtime
path).

Every format carries a top-level **`schemaVersion`** integer. **v1** is the MVP
format. Future binary/compressed formats get their own version (or a sibling
`storageVersion`) and must not break v1 readers — loading a file with an unknown /
newer `schemaVersion` fails fast with a clear, logged error and a migration hint,
never a silent misparse.

### Formats defined (all in `packages/core`, e.g. `schema/map.ts`, `schema/save.ts`, …)

| Format | Path | Contents |
|--------|------|----------|
| **Map** | `schema/map.ts` | `schemaVersion`, map id/name, `tileSize`, dimensions, `tileset` ref, layers (type + tile indices), events list (event pages with commands/conditions), variables/switches |
| **Tileset** | `schema/tileset.ts` | `schemaVersion`, id/name, image atlas ref, per-tile collision flags, animation frames, autotile rules |
| **Save** | `schema/save.ts` | `schemaVersion`, current map id, player position/direction, variables, switches, saved-at timestamp |
| **Editor project** | `schema/project.ts` | `schemaVersion`, project settings (display, initial map, engine options), asset references (images/audio/tilesets/maps), open-editor state |
| **Protocol** | `schema/protocol.ts` | (D14 also covers protocol; reserved for the sync ADR — Q2/RQ4 — kept in `packages/core` so server + clients share it) |

### Concrete example — Save format (v1)

```json
{
  "schemaVersion": 1,
  "savedAt": "2026-08-25T12:00:00Z",
  "mapId": "map_town_square",
  "player": {
    "x": 10,
    "y": 8,
    "direction": "down"
  },
  "variables": { "gold": 50 },
  "switches": { "sw_met_inn_owner": true }
}
```

> The save references the current map by id and stores player position/direction
> plus the exact variable/switch state, so resuming a game is deterministic from a
> single JSON document (portable to IndexedDB or a C++ local file per RQ1).

### Enforcement (required)

- **Schema tests with Vitest** (per D15), colocated as `schema/*.test.ts` in
  `packages/core`: each schema parses its own concrete example above, rejects
  invalid/missing fields, rejects an unknown `schemaVersion`, and (round-trip) a
  parse → serialize → parse cycle is stable. These tests are the gate that makes a
  schema change impossible without its tests being updated.
- **Runtime validation on every load** (editor open, runtime boot, save load) via
  the validation library; failures are logged and surfaced as a readable error, not
  a silent crash.
- **Type sharing:** editor and runtime import the *same* TS types from
  `packages/core`; no duplicated `interface` declarations in either consumer.

## Consequences

### Positive

- **Single source of truth for formats** (with ADR-001): one schema definition
  consumed by editor, runtime, and (later) the protocol — drift is structurally
  impossible.
- **Safe evolution:** `schemaVersion` + fail-fast loading means older readers never
  silently misparse newer files; future binary/compressed storage can coexist
  without breaking v1 (a version-mapping layer, not a rewrite).
- **Portable saves** (RQ1): a save is one self-describing JSON document, valid in
  browser (IndexedDB) and in C++ local-file saves alike.
- **Strong runtime guarantees:** zod (if confirmed) derives the TS type from the
  schema — no two-source type drift — and validates in both browser and Node.
- **Testable gate:** mandatory Vitest schema tests keep the contract honest and
  give a free migration test surface when schemas evolve.

### Negative

- **JSON verbosity/size:** JSON is larger than a binary format; acceptable for MVP
  map/save sizes — the versioning decision keeps a later binary format open without
  breaking v1.
- **Dependency tension with ADR-001:** ADR-001 says the core must stay
  dependency-free; putting the validation library in `packages/core` makes zod (if
  confirmed) the **single documented runtime dependency of the core** — a deliberate
  exception that must be explicitly accepted at review, or the validation code is
  moved to a thin adapter package that the core types live beside.
- **Migration cost on version bumps:** bumping `schemaVersion` for a real schema
  change requires a migration path for existing maps/saves; this is an ongoing
  maintenance cost, mitigated by keeping v1 changes behind additive-only rules
  during MVP.
- **Schema/setup ceremony before gameplay code:** formats must be specified and
  tested before the editor/runtime can talk to each other — which is exactly the
  WAL ordering (docs/03-wal-process.md) the project already requires.
