# ADR-004 — Multiplayer protocol v1 (WebSocket + JSON)

## Metadata

- **Status:** proposed
- **Date:** 2026-08-25
- **Author:** Design-C (Architecture Design member)

## Status

- **Status:** proposed
- **Supersedes:** none

## Context

Multiplayer for the MVP is a **2-player relay sync**: 2+ clients connect over
**WebSocket to ONE C++ server** that relays and broadcasts player position/state,
with **no NAT punch-through / P2P** ([RQ4, docs/02-open-questions.md](../02-open-questions.md)).
The server is a **relay / state-sync server** — a thin pipe that also stores state;
game logic runs client-side; the protocol must be **versioned** so an authoritative
server can be added later ([Q2, docs/02-open-questions.md](../02-open-questions.md)).

The **MVP sync scope is players only**: position / direction / animation,
join/leave, and chat. **World-state sync (doors/switches/NPCs) is a documented MVP
limitation** ([D16, docs/02-open-questions.md](../02-open-questions.md)).

Data formats are **versioned JSON schemas (shared TS types) for maps / events /
saves / protocol** ([D14, docs/02-open-questions.md](../02-open-questions.md)). The
project is agent-developed with the WAL process ([docs/03-wal-process.md](../03-wal-process.md)),
so the wire format must be human-readable and directly debuggable from server logs.
The C++ server implements this protocol (see [ADR-005](./ADR-005.md)).

## Decision

**Multiplayer protocol v1 = WebSocket transport + JSON payloads.** Every message is
a JSON envelope that **carries a protocol version field `v` in EVERY message**, a
`type` naming the message from the catalog below, and a `payload` object. Sync scope
is **players only** in the MVP (D16); world-state sync is a documented limitation with
reserved extension points.

### Envelope (every message)

```json
{
  "v": 1,
  "type": "player_state",
  "seq": 7,
  "payload": { }
}
```

| Field | Required | Type | Meaning |
|-------|----------|------|---------|
| `v` | yes | integer | Protocol version. **Present in EVERY message** (both directions). `1` = v1. |
| `type` | yes | string | One of the message catalog names below. |
| `seq` | no | integer | Per-connection monotonically increasing sequence (useful for debugging and future reliability work; client fills, server echoes where relevant). |
| `payload` | yes | object | Message-specific body, defined per type below. |

### Message catalog

| Type | Direction | Purpose |
|------|-----------|---------|
| `hello` | C→S | Join a room (first message of a connection). |
| `welcome` | S→C | Room info + current players + assigned session id (reply to `hello`). |
| `player_state` | C→S, S→C | Position / direction / animation update (**rate-limited**); C→S carries a client timestamp, S→C is the broadcast to other players. |
| `chat` | C→S, S→C | Send / relay chat text. |
| `leave` | C→S, S→C | Client leaves a room (C→S), server notifies the others (S→C), then closes. |
| `ping` / `pong` | C→S / S→C | Heartbeat; `pong` echoes the client timestamp. |
| `error` | S→C | Protocol / version / rate-limit failures. |

All coordinates below are in **tile units** (not pixels) for v1; animation is a
string token from the runtime's shared catalog (e.g. `idle`, `walk`).

#### `hello` (C→S) — join

```json
{
  "v": 1,
  "type": "hello",
  "seq": 1,
  "payload": {
    "playerName": "Aria",
    "roomId": "room-alpha",
    "projectId": "prj-sunrise-valley"
  }
}
```

- Must be the **first** message on a connection. A second `hello` is an error
  (`protocol_error`).
- `roomId`: logical session/room identifier (MVP uses a single room name; the room
  registry in ADR-005 keys on this).
- `projectId`: optional; lets the server reject clients running a different project
  from joining the same room (`project_mismatch` error) — MVP servers may ignore it.

#### `welcome` (S→C) — room info + current players

```json
{
  "v": 1,
  "type": "welcome",
  "seq": 1,
  "payload": {
    "sessionId": "s-01ab",
    "roomId": "room-alpha",
    "projectId": "prj-sunrise-valley",
    "serverTimeMs": 1756100000000,
    "players": [
      { "sessionId": "s-01aa", "playerName": "Kibo", "state": { "x": 16, "y": 12, "direction": "down", "animation": "idle" } },
      { "sessionId": "s-01ab", "playerName": "Aria", "state": { "x": 15, "y": 12, "direction": "left", "animation": "idle" } }
    ]
  }
}
```

- `players` = the current occupants **including the joiner**, so every client can
  reconstruct the room from the same source of truth.
- `serverTimeMs` enables client↔server clock-skew estimation (see Consequences).

#### `player_state` (C→S) — client update, rate-limited

```json
{
  "v": 1,
  "type": "player_state",
  "seq": 12,
  "payload": {
    "state": { "x": 16.5, "y": 12.0, "direction": "down", "animation": "walk" },
    "clientTimeMs": 1756100000123
  }
}
```

- `clientTimeMs`: client timestamp at the moment the state was captured (used for
  latency/heartbeat math and future interpolation; **not** for authoritative ordering).
- **Rate limit:** server enforces a default of **10 Hz per client** (token bucket,
  burst 15). Excess updates are **coalesced** (the latest state wins; intermediate
  ones dropped) rather than queued — position state is self-replacing. Sustained
  abuse beyond ~3× the limit triggers `rate_limited` errors then disconnect.

#### `player_state` (S→C) — broadcast to the others

```json
{
  "v": 1,
  "type": "player_state",
  "seq": 11,
  "payload": {
    "sessionId": "s-01aa",
    "state": { "x": 16.5, "y": 12.0, "direction": "down", "animation": "walk" },
    "clientTimeMs": 1756100000123,
    "serverTimeMs": 1756100000141
  }
}
```

- Server adds the sender's `sessionId` and its own receipt time. Sent to **all other
  players in the room** (never echoed to the sender — the sender already knows).

#### `chat` (C→S)

```json
{
  "v": 1,
  "type": "chat",
  "seq": 20,
  "payload": { "text": "hello, Kibo!" }
}
```

#### `chat` (S→C) — broadcast

```json
{
  "v": 1,
  "type": "chat",
  "seq": 19,
  "payload": {
    "sessionId": "s-01ab",
    "playerName": "Aria",
    "text": "hello, Kibo!",
    "serverTimeMs": 1756100000200
  }
}
```

- Chat is **rate-limited**: default **2 messages/sec, 200 chars max** per client.
- Server never logs chat text by default (see ADR-005 logging rules).

#### `leave` (C→S)

```json
{
  "v": 1,
  "type": "leave",
  "seq": 21,
  "payload": { "reason": "user_quit" }
}
```

#### `leave` (S→C) — notify the others, then close

```json
{
  "v": 1,
  "type": "leave",
  "seq": 20,
  "payload": { "sessionId": "s-01ab", "playerName": "Aria", "reason": "user_quit" }
}
```

- The server sends the S→C `leave` to the remaining room members **before** closing
  the leaving client's connection. `reason` values are free-form strings for MVP
  (`user_quit`, `disconnect`, `server_shutdown`, …).
- Abrupt TCP drops are detected via the heartbeat (below): if a connection goes
  silent, the server treats it as a `leave` with `reason: "timeout"`.

#### `ping` (C→S) / `pong` (S→C) — heartbeat

```json
{ "v": 1, "type": "ping", "seq": 25, "payload": { "clientTimeMs": 1756100015000 } }
```

```json
{ "v": 1, "type": "pong", "seq": 24, "payload": { "clientTimeMs": 1756100015000, "serverTimeMs": 1756100015030 } }
```

- Client pings every **15 s**; server replies `pong` echoing `clientTimeMs` (round-trip
  latency = `pong` receipt time − `clientTimeMs`).
- If the server sees **no message of any kind for 60 s**, the connection is considered
  dead and is closed as a `leave` (`reason: "timeout"`).

#### `error` (S→C)

```json
{
  "v": 1,
  "type": "error",
  "seq": 3,
  "payload": {
    "code": "protocol_version_mismatch",
    "message": "server requires protocol version 1",
    "detail": { "serverVersion": 1, "clientVersion": 2 }
  }
}
```

Error codes for v1:

| Code | Meaning |
|------|---------|
| `protocol_version_mismatch` | `v` field differs from what the server supports (server then closes). |
| `malformed_message` | Not valid JSON / missing required envelope fields / wrong payload shape. |
| `unknown_type` | `type` not in the catalog (client should log + ignore; server replies once per connection). |
| `protocol_error` | e.g. second `hello`, `hello` not first, out-of-sequence state. |
| `room_not_found` | `hello` names a `roomId` that does not exist (MVP may auto-create; if not, this code). |
| `room_full` | Room reached its player cap (default 16, server-configurable). |
| `name_taken` | `playerName` already in the room. |
| `project_mismatch` | `projectId` differs from the room's project. |
| `rate_limited` | Client exceeded a rate limit (chat/state/hello). |
| `internal_error` | Anything else; server logs the detail, client sees a generic message. |

### Rate / backpressure guidance

Defaults below are **server-configurable** and must be validated with real gameplay
during implementation (see ADR-005 tests):

| Stream | Default limit | On excess |
|--------|---------------|-----------|
| `player_state` | 10 Hz / client (burst 15) | coalesce (keep latest), drop intermediate |
| `chat` | 2 msg/s / client, 200 chars | drop + `rate_limited`; repeat abuse → disconnect |
| `hello` | once per connection | `protocol_error` |
| Message size | 4 KiB max per message | `malformed_message`, then close if repeated |
| Outbound queue / connection | bounded (≈512 queued messages) | drop oldest `player_state` broadcasts (state is self-replacing); **never drop `chat`/`leave`/`welcome`/`error`** |
| Slow consumer | outbound queue full > 5 s | server closes the connection |
| Idle timeout | no traffic for 60 s | server closes as `leave` (`timeout`) |

Rules of thumb baked into the above:

1. **State is self-replacing** — when a client or the server is behind, drop the
   intermediate positions, keep the newest; never buffer position history.
2. **Control messages are never dropped** — `welcome`, `chat`, `leave`, `error` go
   through a FIFO path and are only dropped by closing the connection if the queue
   stays full (slow-consumer protection).
3. **Bounded memory everywhere** — per-connection inbound size cap and outbound queue
   cap prevent a single bad client from exhausting server memory.
4. **Coalesce before you rate-limit, rate-limit before you disconnect.**

### Extension points (future world-state sync & authoritative server)

- **New message types are additive.** Clients ignore `type` values they do not
  recognize (log a `warn`, do not die); servers reject unknown `type` from clients
  with `unknown_type` once per connection. This lets new messages roll out without a
  version bump.
- **Version bump policy.** Bump `v` (breaking change) only when existing types/fields
  are removed, renamed, or change meaning. Additive fields/messages keep `v` the
  same. On mismatch the server replies `protocol_version_mismatch` and closes, so a
  v1 client never mis-parses a v2 stream.
- **Reserved world-state types** for phase 2 (host-authoritative world state per
  Q2/D16): `world_state` (S→C full snapshot), `world_state_delta` (S→C incremental),
  `world_action` (C→S, e.g. flip switch, open door, talk to NPC). Their semantics are
  **undefined in v1** and are not sent by an MVP server.
- **Authoritative-server readiness.** The envelope already distinguishes transport
  (`v`/`seq`), the message kind (`type`), and the body (`payload`); fields that are
  client-authored in v1 (e.g. `state`) can become server-authored without changing
  the envelope. `clientTimeMs`/`serverTimeMs` give the telemetry needed for latency
  compensation and clock-skew analysis later.
- **Shared JSON schema.** The normative field-level schema (D14, shared TS types in
  `packages/core`) will mirror this ADR once implemented; the C++ server cannot
  import TS, so **this ADR is the normative wire description for the server** and its
  Catch2 protocol tests.

## Consequences

### Positive

- **Human-readable, agent-friendly wire format** — logs can be read directly, which
  fits the WAL/logging culture ([docs/03-wal-process.md](../03-wal-process.md)) and
  AI-agent debugging.
- **Version field in every message** → graceful protocol evolution and clear,
  unambiguous mixed-version failure (`protocol_version_mismatch`), preserving the
  option to add an authoritative server later (Q2).
- **Players-only scope (D16)** keeps the server thin, stateless-per-room and
  low-latency — exactly the MVP size.
- **Explicit rate/backpressure rules** prevent the classic multiplayer failure modes
  (flood abuse, memory exhaustion, slow-consumer stalls) before they happen.
- **Reserved extension points** mean phase-2 world-state sync (doors/switches/NPCs)
  can land without redesigning the envelope.

### Negative

- **JSON over binary** costs bytes and parse time vs. a packed binary protocol —
  acceptable at MVP scale (10 Hz × a handful of players), measurable later with the
  server timing logs (ADR-005).
- **No world-state sync in the MVP (D16)** — doors/switches/NPCs visibly desync
  between players. This is a **documented MVP limitation** and must be surfaced in
  the product, not hidden.
- **Rate limits need calibration** with real gameplay; too aggressive = jittery
  movement, too loose = abuse. Tuning is follow-up work (ADR-005 tests + field
  testing).
- **Client timestamps assume best-effort clocks** — used for latency math only, never
  for authoritative ordering; must not leak into gameplay logic.
- **No TLS/WSS in v1** — plain WebSocket is fine for LAN/dev/VPS with trusted users,
  but public deployment must revisit transport security (phase 2, out of scope here).
