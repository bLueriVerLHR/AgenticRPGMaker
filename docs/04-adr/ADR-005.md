# ADR-005 — C++ relay / state-sync server (single binary, Linux)

## Metadata

- **Status:** proposed
- **Date:** 2026-08-25
- **Author:** Design-C (Architecture Design member)

## Status

- **Status:** proposed
- **Supersedes:** none

## Context

The C++ component is the **launcher/server that serves content and hosts
multiplayer**. Under the D-numbering, **D9 = RQ3** (server stack) and **D10 = RQ4**
(multiplayer model); both are **decided** in
[docs/02-open-questions.md](../02-open-questions.md):

- **RQ3 (D9) — stack:** C++20 + standalone Asio + websocketpp (header-only via CMake
  FetchContent) + **custom HTTP static hosting** + spdlog + Catch2 + CMake.
- **RQ4 (D10) — model:** 2+ clients connect over WebSocket to **ONE C++ server** (on
  a Linux box or cloud VPS) that **relays and broadcasts** player position/state; **no
  NAT punch-through / P2P in MVP**.
- **Q2:** the server is a **relay / state-sync server** — a thin pipe that also stores
  state; game logic runs client-side; versioned protocol so an authoritative server
  can be added later.
- **Q1/Q5:** the server also **serves content** — the portable `www` package (single
  player, "double-click and play") **and** the editor build; C++ targets **Linux only**
  in the MVP.
- **Q6:** MVP includes the C++ Linux launcher/server serving content and 2-player
  relay sync.
- **WAL process** ([docs/03-wal-process.md](../03-wal-process.md)) mandates: spdlog
  logging (server lifecycle, connections, protocol errors, timings; **never log
  secrets**), and Catch2 tests before any real-environment run.
- The wire protocol this server implements is defined in **[ADR-004](./ADR-004.md)**
  (Multiplayer protocol v1).

## Decision

Build **one CMake C++20 executable, Linux target**, that serves **both** the portable
`www` package **and** the editor build over custom HTTP **and** hosts the multiplayer
WebSocket endpoint, using:

- **C++20**, **standalone Asio** + **websocketpp** (both header-only, fetched via CMake
  `FetchContent` — no system installs, reproducible config).
- **Custom HTTP static file serving** (serves the portable `www` package AND the
  editor build) with strict path canonicalization and a minimal MIME map.
- **Room registry** — rooms keyed by `roomId`, members with their last-known
  `player_state` (the "state storage" of the relay).
- **Relay / broadcast logic** — implements ADR-004: forward `player_state`/`chat` to
  the other room members, handle `hello`/`welcome`/`leave`, heartbeats, error codes.
- **Per-client rate limiting** — token buckets per message class with the ADR-004
  defaults (state 10 Hz, chat 2/s, hello once, 4 KiB message cap, bounded outbound
  queues with coalescing + slow-consumer disconnect).
- **spdlog logging** — server lifecycle, connections, protocol errors, per-message
  timing at `debug`; log level configurable at runtime; **never log secrets** (see
  below for the concrete policy).
- **Catch2 tests** — unit tests for the room registry, rate limiter, message
  parse/validate, queue/backpressure logic, HTTP path mapping/MIME; plus a loopback
  **integration test** that boots the server and drives real WebSocket clients
  through hello → welcome → broadcast → rate-limit → leave.
- **CMake single binary** target (suggested name `agenticrpg-server`).

### Component layout (MVP)

```
agenticrpg-server (one executable)
├── HTTP static file server      → serves www/ (portable package) + editor/dist/
├── WebSocket endpoint           → /ws (protocol v1 per ADR-004)
├── Room registry                → rooms × members × last state (shared state store)
├── Relay / broadcast            → per-room fan-out with per-client outbound queues
├── Rate limiter                 → token buckets per client per message class
├── Config / CLI                 → --www-root --editor-root --port --log-level --max-players-per-room
└── Logging                      → spdlog (levels per WAL doc)
```

### Key implementation commitments

1. **One port, two protocols.** websocketpp handles the WebSocket upgrade; the HTTP
   server is custom (websocketpp also exposes raw HTTP request handling, which we use
   for static files). Single listening socket, default port **8080**, overridable via
   CLI/env (`AGENTICRPG_PORT`).
2. **Static serving safety.** Paths are canonicalized, `..`/absolute/encoded traversal
   is rejected, MIME types come from an explicit allow-list map, directory requests
   serve `index.html`, and there is no CGI/exec of any kind. This is security-relevant
   code (see Negative).
3. **Threading: single `io_context`, one thread for MVP.** Deliberately simple and
   deterministic for tests. The upgrade path (multiple threads calling
   `io_context::run()` with a strand per connection) is a config change, not a
   rewrite, but is out of scope for MVP.
4. **Rate limiting + backpressure** live on the server even though the server is a
   thin relay — a relay is exactly where floods land. Defaults come from
   [ADR-004](./ADR-004.md) (coalesce state, never drop control messages, bounded
   queues, slow-consumer disconnect).
5. **Logging policy (WAL doc §2):**
   - `info`: startup, config, listening address/port, shutdown, connect/disconnect,
     handshake result.
   - `debug`: per-message timing/latency, per-room events.
   - `warn`/`error`: protocol errors (malformed, version mismatch, unknown type,
     rate-limit abuse) always with enough context to reproduce.
   - **Never logged:** passwords, tokens, API keys, session secrets, auth material.
     **Chat text is not logged by default** (personal data); player names are logged
     only at `info`/`debug` for session diagnostics. Level is runtime-configurable via
     CLI/env (`AGENTICRPG_LOG_LEVEL`), never hard-coded.
6. **Tests are part of the build.** `FetchContent` pulls Catch2; unit tests run headless
   with no sockets; the loopback integration test is tagged `[integration]` and is part
   of the required suite before any real-environment run (WAL doc §3).
7. **FetchContent pins** Asio, websocketpp, spdlog, Catch2 to exact versions in
   `CMakeLists.txt` for reproducible builds (with a documented vendoring fallback for
   offline builds).

### Implementation notes (verified against implementation, P6)

Confirmed against the shipped server (`server/src/*`, merged to main @ 94da8da):

- **`defer_http_response()` is required before `send_http_response()`.** In the
  websocketpp HTTP handler, calling `con->send_http_response()` without a prior
  `con->defer_http_response()` throws `invalid_state`. The server therefore calls
  `defer_http_response()` first, then writes and sends the response
  (`server/src/server.cpp`, HTTP static handler).
- **No-TLS builds use the `asio_no_tls` configs.** Because TLS/WSS is out of MVP
  scope, the server includes
  `<websocketpp/config/asio_no_tls.hpp>` and uses
  `websocketpp::config::asio` / `websocketpp::config::asio_client` — **not**
  `websocketpp/config/asio.hpp` (which pulls in OpenSSL) (`server/src/server.hpp`).
- **Room join auto-creates the room.** ADR-004's `room_not_found` error is kept for
  completeness, but in the shipped MVP the server calls `getOrCreateRoom(roomId)`
  on `hello` **before** joining, so joining a not-yet-existing room succeeds
  (MVP auto-create, per ADR-004's "MVP may auto-create") (`server/src/server.cpp`,
  `server/src/room_registry.*`).

## Consequences

### Positive

- **Single binary, tiny dependency surface** — scp one file to a Linux box/VPS and it
  serves the game + hosts multiplayer (matches Q1 "double-click and play" for
  single-player and RQ4 for multiplayer).
- **Header-only deps via FetchContent** — no system package installs, reproducible
  configuration, deterministic pins.
- **Custom static serving removes a runtime dependency** and keeps the launcher story
  one binary; no separate nginx/apache in the dev loop.
- **Relay + rate limiting on the same process** means the abuse protections and the
  protocol live next to each other and are tested together.
- **Single-threaded MVP core** is deterministic and trivially testable; the
  multithreading upgrade path is a documented config change.
- **spdlog + explicit logging rules** satisfy the WAL hard requirement (logging) and
  the "never log secrets" rule is explicit, not incidental.
- **Catch2 unit + loopback integration tests** satisfy the mandatory-testing gate
  before any real-environment run.

### Negative

- **Custom HTTP server is security-relevant code** — path traversal, MIME, resource
  exhaustion (slowloris, giant requests). Mitigated by canonicalization + allow-lists
  + bounded request sizes + tests, but it is a hand-rolled surface; if it grows
  complex, revisit a hardened static server (follow-up).
- **FetchContent needs network at configure time** — offline environments need
  vendored deps or a package mirror (documented fallback).
- **Linux-only (Q5)** — Windows/macOS server builds are explicitly out of MVP scope;
  the cross-platform problem is deferred.
- **No TLS/WSS in MVP** — fine for LAN/dev/VPS with trusted users; must be revisited
  before public deployment (transport security is a phase-2 concern, not decided
  here).
- **Single-threaded relay caps throughput** — fine for MVP (a handful of players at
  10 Hz), but the limit is real; measured via the `debug` timing logs, not assumed.
- **JSON parse cost on every message** — acceptable at MVP scale; benchmark during
  implementation and revisit if profiling demands a binary codec (would be a new ADR).
