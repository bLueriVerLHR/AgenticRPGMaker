## Context

The editor (Game Maker) is a **web application launched by the C++ binary**, which
serves the editor's HTML pages ([Q1/Q5, docs/01-vision.md](../01-vision.md); vision §4).
Decided defaults in [docs/02-open-questions.md](../02-open-questions.md):

- **D12 — storage:** browser **IndexedDB** for MVP (portable/offline), with
  **import/export to folder**; C++ server file persistence deferred to phase 2.
- **D13 — UI:** **React + TypeScript + Vite (editor only)**; the **game runtime stays
  framework-free vanilla TS** for portability.
- **D14 — data formats:** versioned **JSON schemas (shared TS types)** for
  maps/events/saves/protocol.
- **D15 — repo structure:** monorepo `packages/core`, `packages/renderer`,
  `packages/runtime`, `packages/editor` + `server` (C++) + `samples`; **pnpm
  workspaces**; **Vitest + Playwright + Catch2**.
- **Q4 — scripting:** visual event pages + TypeScript script API; **Q6 — MVP
  scope:** map editor (tile layers + events) + single-player runtime + 2-player relay
  sync.
- **D16:** multiplayer sync covers players only; world-state sync is a documented MVP
  limitation (the editor therefore creates events/maps, but doors/switches/NPCs are
  not synchronised in the MVP runtime).

The editor and the runtime must **not drift**: the map you draw in the editor must be
the map the runtime walks, and the events you place must behave identically in the
preview and in the shipped game. This drives the "share `packages/core`" decision
below.

## Decision

**The editor is an editor-only package (`packages/editor`) built with React +
TypeScript + Vite (D13).** It stores projects in the browser's **IndexedDB with
import/export to a folder** (D12), and it **shares `packages/core` (data model + event
interpreter) with the runtime**, so editor and game are one implementation.

### Editor feature set (MVP, per Q6)

1. **Tile layers** — layered tilemaps with the versioned map JSON schema (D14);
   layer visibility/order controls.
2. **Paint brush** — paint tiles onto layers from an asset picker (same asset
   manifest the runtime loads).
3. **Event placement** — drop events (from the visual event catalog + TS script hooks,
   Q4) onto tiles; events are saved in the shared schema and interpreted by
   `packages/core` at runtime.
4. **Project tree** — maps, assets, and the current map's global data
   (variables/switches) navigable and editable.
5. **Variables/switches panel** — edits the **current map's** variables/switches
   (per-map, on the map document — `mapSchema.variables` / `mapSchema.switches`);
   there is **no project-global common-events schema in core v1** (see
   implementation note below).
6. **Run-preview** — a preview mode that **embeds the runtime** (same
   `packages/runtime` + `packages/core`, rendered in an isolated in-editor surface /
   iframe) so "preview" is literally the game.

> **Implementation note (verified against implementation, P6):** core v1 has **no
> common-events schema** — variables and switches live **per-map** on the map
> document (`mapSchema.variables` / `mapSchema.switches` in
> `packages/core/src/schema/map.ts`), not project-global. The editor's **Global Data
> panel edits the current map's variables/switches** (see
> `packages/editor/src/ui/VariablesPanel.tsx` / `ProjectTree.tsx`). Project-global
> variables/common events would require a **core schema addition (future)**. Also per
> the task spec, **export produces `data/` + a `README.md` (no `index.html`
> harness)** — the portable `www` `index.html` is produced by the P5 packaging
> scripts, not by the editor export.

### Storage & import/export (D12)

- MVP storage is **IndexedDB** (offline, portable, no server round-trip for
  single-player editing), behind a thin async repository interface so a later
  server/file backend can swap in.
- **Import/export to a folder** is implemented as a **project package**:
  - **Export:** the editor serialises the project to the `www`-style folder layout
    (maps, events, assets, `index.html` harness for the sample) and downloads it as a
    **ZIP archive** (or, in Chromium browsers where the File System Access API is
    present, offers a "save to folder…" upgrade path).
  - **Import:** the editor accepts the same ZIP **or a folder picked via a file
    input** (`webkitdirectory`), validates it against the shared schema, and loads it
    into IndexedDB.
  - The **File System Access API is never required** and never used by the portable
    runtime (see [docs/08-compatibility-checklist.md](../08-compatibility-checklist.md));
    in the editor it is only an optional convenience.
- **Autosave** into IndexedDB on change (debounced) so an accidental refresh does not
  lose work; an explicit export is the user's backup path (see Negative: origin-tied
  storage).

### Build & tooling

- **Vite** dev server for fast editor development (HMR), and a production build; the
  **editor build output (`dist/`) is served by the C++ server** (ADR-005) or any
  static host (Q1).
- **pnpm workspace** package `packages/editor` (D15); shared TS types and the event
  interpreter come from `packages/core`; the runtime (`packages/runtime`,
  `packages/renderer`) is a dependency for preview only.
- **Tests:** **Vitest** for editor unit/component tests (storage repository,
  serialization, tool state machine — D15); **Playwright** E2E for the editor flows
  (create project → paint tiles → place event → run preview).

## Consequences

### Positive

- **Editor and runtime share `packages/core`** — one data model, one event
  interpreter; **preview cannot drift from the shipped game** (the single biggest
  correctness win for a game editor).
- **IndexedDB storage is offline/portable** (RQ1 aligns) and needs no server; the
  import/export package gives users real ownership of their project files.
- **React + TS + Vite** is a fast, well-trodden stack for a complex UI tool; the
  framework stays **editor-only**, so the portable runtime remains lean vanilla TS
  (D13) and the compatibility surface (docs/08) stays small.
- **Run-preview embedding the runtime** gives instant feedback — matching the
  project's "logs + tests + docs" culture with a tight edit→run loop.
- **Versioned shared JSON schemas (D14)** make the editor's output the runtime's
  input without translation layers.

### Negative

- **IndexedDB is origin-tied** — a cleared browser profile or different origin can
  orphan projects. Mitigations: autosave + visible "export your project" prompts,
  import/export as a first-class flow, docs for users. This is a real UX trap, not a
  footnote.
- **Editor-only complexity stays editor-only** — React must not leak into
  `packages/runtime`; the shared boundary (`packages/core`) is rigorously
  framework-free, or portability of the runtime is silently lost (guard in code
  review/tests).
- **File System Access API is Chromium-only** — the universal ZIP import/export
  avoids depending on it, but the "export to a real folder" UX is degraded outside
  Chromium until a better primitive exists.
- **IndexedDB async/quota semantics** need a careful repository layer (transactions,
  versioning, quota errors) — plus tests; a naive implementation introduces subtle
  data-loss bugs.
- **ZIP packaging needs a library dependency** (e.g. jszip) — adds a (small) dep to
  the editor; acceptable for a dev tool, must not reach the runtime.
- **Preview embedding is not free** — iframe isolation (or in-tree runtime) has
  pointer-event, focus, and asset-loading subtleties that Playwright E2E must cover.
