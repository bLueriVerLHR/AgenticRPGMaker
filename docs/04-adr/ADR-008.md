# ADR-008 — Portable-First Engine: Editor-less Authoring & Multi-Backend Abstraction

## Metadata

- **Status:** proposed
- **Date:** 2026-08-31
- **Author:** Agent (docs workstream, per 2026-08-31 re-orientation discussion)

## Status

- **Status:** proposed
- **Supersedes:** partially supersedes **ADR-006** (Web editor) — the editor is
  removed from `main` and archived via git tag (D20); this ADR records the
  portable-first / editor-less / multi-backend direction that replaces it.

## Context

The repository re-orientation (2026-08-31) — see
[docs/discussion/2026-08-31-reorg.md](../discussion/2026-08-31-reorg.md) — decided:

- **D20** — remove `packages/editor` from `main`; archive via git tag; add back
  when a real game exists.
- **D21** — portable-first engine: one engine that runs, unmodified, on every
  target in scope (browser + JoiPlay today). JoiPlay runs RPG Maker MV/MZ from
  their `www` HTML5 folder (verified from JoiPlay's own FAQ), so our portable
  `www` package is a first-class JoiPlay target. Backends are configurations of
  the same runtime, selected by a thin platform-capability layer.
- **D22** — the C++ server (ADR-005) is demoted to an optional component.
- **D23** — portable first; reserve WebGPU renderer backend + WASM core as
  future seams, no investment now.
- **D24** — AI/agent-authored versioned JSON is the primary creation path, with
  a CLI validation entry point as the agent gate.

This is a correction of the original MVP framing (Q1–Q6 / RQ1–RQ5, D12–D19):
the original plan treated the editor as a first-class MVP workstream (P2, WS2,
ADR-006). Reality (auto-generated development) means the editor is not needed
before a real game exists, and portability across browser + JoiPlay is the
priority over raw performance.

## Decision

**Adopt a portable-first engine model:**

1. **Editor-less authoring (D20, D24).** `packages/editor` is removed from
   `main` and archived via git tag (`archive/editor-0.1.0`). Game content is
   authored as **versioned JSON documents** (maps/events/dialogue/tilesets/
   projects) validated by `packages/core` schemas (ADR-003). A **CLI validation
   entry point** (`pnpm validate`, `scripts/validate.mjs`) is the agent-facing
   gate. The data model (`core`) is the single source of "what is legal" — any
   rule that used to live in the editor's map-ops/command-stack is a validation
   rule in `core`.

2. **One runtime, many backends (D21, D23).** The renderer stays behind the
   `Renderer` interface (ADR-002): WebGL default + Canvas2D fallback today, with
   the interface shaped to admit a future **WebGPU backend** (reserved seam, not
   implemented now). The core interpreter is kept separable for a future **WASM
   build** (reserved seam). A thin `PlatformCapabilities` probe (renderer
   support, input devices, storage, audio) configures the existing seams
   (Renderer / Storage / Transport / Input / Behavior) — browser and JoiPlay are
   **configurations of the same runtime**, never separate programs.

3. **C++ server optional (D22).** The server (ADR-005) remains a maintained,
   optional component (multiplayer relay + static hosting); the portable
   single-player engine never requires it.

## Consequences

### Positive

- **Smallest movable surface.** Removing the editor deletes an entire React/Vite
  package from the build/test/deploy graph; agents and humans reason about a
  leaner repo (core → renderer → runtime + optional server).
- **AI-native authoring.** With JSON as the interchange and `core` as the
  legality authority, an LLM can produce a playable game end-to-end (survey
  evidence: `rpg-maker-agent`, `Shinsekai`), and the CLI validator gives agents a
  deterministic gate (D24).
- **JoiPlay as a first-class target, for free.** Our portable `www` package is
  exactly what JoiPlay already runs for MV/MZ; no separate JoiPlay runtime/build
  is needed (D21).
- **Performance has a place to land later.** WebGPU renderer + WASM core are
  reserved seams, so portability work today does not paint the architecture into
  a corner (D23).

### Negative

- **No visual editing for now.** Authors write/feed JSON rather than clicking a
  map editor; the human-friendliness of authoring depends on the schema quality
  and the CLI (mitigated by `core` validation error quality; the editor is
  recoverable from the archive tag when a game justifies it).
- **Editor code drifts while archived.** When restored, `packages/editor` will
  need to be re-synced to any `core` model/schema changes that happened while it
  was archived (D20 mitigates by keeping the data model the contract).
- **Optional server is easy to neglect.** The C++ relay may rot if no one runs
  the multiplayer path; the QA gate keeps its build/tests green but product
  focus is single-player.
- **Reserved seams are not implemented.** WebGPU/WASM remain future work; teams
  must not mistake "reserved" for "scheduled".

## Supersedes

Supersedes **ADR-006** (Web editor, React + TypeScript + Vite) — editor removed
from `main` and archived (D20). Complements ADR-001 (core data model), ADR-002
(renderer interface), ADR-003 (versioned JSON), ADR-005 (optional C++ server).
