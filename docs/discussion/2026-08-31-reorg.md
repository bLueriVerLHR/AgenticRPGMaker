# Discussion — 2026-08-31 Repository Re-orientation

> Status: **consensus reached**. All decisions below were answered by the user in
> this discussion. This record is the verbatim source of the choices that the
> rest of the re-org (principle/, task/, ADRs, updated docs) implements.

## Trigger

The user asked to: (1) survey open-source projects (Tyrano / open-source RPG
engines and games), (2) re-organize the docs and the development branches, and
(3) re-examine how the repository should be designed. Because development is
primarily auto-generated code (AI agents), the editor should be removed first
and added back once a real game takes shape. The engine should be like RPG Maker
but more customizable, and abstracted so it runs on more backends (today:
browser and JoiPlay).

## Survey takeaways (facts, verified)

Reference implementations examined via GitHub/GitLab:

- **TyranoScript** (`ShikemokuMK/tyranoscript`): JS visual-novel engine
  (Browser/iOS/Android). `data/scenario/*.ks` KAG-style tag scripts + `tyrano/`
  runtime + `tyrano/plugins/*` plugin hooks. Primarily a **VN** engine (no tile
  maps / combat / RPG data model) — useful for its command/tag + plugin model,
  not as an RPG engine blueprint.
- **RPG Paper Maker** (`RPG-Paper-Maker/*`, TS/React/three.js/Howler/Electron):
  editor and runtime are **separate repositories**; the runtime
  (`Game-Scripts`) interprets versioned JSON through an `Interpreter.ts` +
  `Core/` + `Data/` split. Multi-platform (Web/Windows/Linux/macOS). Closest
  structural analog to our core → runtime split.
- **EasyRPG/Player** (C++): interpreter that runs RPG Maker 2000/2003 data
  directly; multi-platform (incl. Android/iOS). Pure-interpreter route.
- **mkxp / mkxp-z** (C++): RGSS runtime for RM XP/VX/VX Ace; **what JoiPlay
  uses** for those engines.
- **JoiPlay** (Android): official FAQ confirms it runs **Ren'Py, RPG Maker
  XP/VX/VX Ace/MV, TyranoBuilder, and any HTML-based engine**; MV/MZ are run
  from their **`www` HTML5 folder** (MV: `www/js/plugins.js`, MZ: `js/plugins.js`).
  ⇒ Our portable `www` package is a first-class JoiPlay target; browser and
  JoiPlay can share the same runtime, differing only in input (JoiPad), renderer
  capability (CrossWallk exists precisely for weak WebGL), and storage limits.
- **Auto-code references**: `karminski/rpg-maker-agent` (LLM pipeline that
  generates a playable RPG Maker MZ project from a text article), and
  `RachelForster/Shinsekai` (AI RPG maker). Both demonstrate: **if the data
  format (JSON schema) + runtime interpreter are good enough, a game can be
  authored entirely by AI/agents without a visual editor.**

## Decisions (user answers, verbatim intent)

### Q1 — Work order
- **Chosen:** align the new repository design direction **first**, then do the
  docs + branch re-org once — avoid doing it twice.

### Q2 — Editor disposition
- **Chosen (with C1 refinement):** archive via **git tag only** and **delete the
  `packages/editor` files** from `main`. History stays in git; restore = `git
  checkout <tag>` + move the package back. No file copy kept in the tree.

### Q3 — Documentation system
- **Chosen:** **keep the WAL skeleton** (01–08 + ADRs) and **add discussion /
  principle / task records** (`docs/discussion`, `docs/principle`, `docs/task`)
  capturing this re-org's decisions. Evolve, do not tear down.

### Q4 — Multi-backend scope (user clarification)
- User clarified: the point is **first a portable engine that runs on every
  target component/environment (browser, JoiPlay, more later); then research
  higher-performance paths (vgpu, wasm)**. Not "model JoiPlay as a separate
  backend."

### Q5 — C++ server
- **Chosen:** **keep but demote to an optional component.** Single-player engine
  + portable package is the core; the C++ relay server is a later/optional piece,
  not a first-class MVP target.

### Q6 — Performance route
- **Chosen:** **portable first** (Canvas2D+WebGL running today), **reserve
  WebGPU renderer backend and WASM core as future switching points** — design
  the seams now, do not invest now.

### Q7 — Authoring workflow (the "auto-code" mainline)
- **Chosen:** **AI/agent-authored JSON is the primary creation path** — AI emits
  versioned JSON (maps/events/dialogue) → `core` validates → runtime runs. Data
  format is designed to be **AI/hand-write friendly + strictly validated**, and
  a **CLI validation entry point** exists as the agent interface.

### Q8 — Branch re-org (user clarification)
- User: **merge what can be merged, delete the rest — a new development approach
  is needed.** (Refined by C3/C4: archive locally via tags, do **not** push-delete
  remote branches; new workflow = module-scoped short-lived branches +
  validate-first.)

### Q9 — Scope of this pass
- **Chosen:** **docs + branch re-org + code-side editor removal in one pass** —
  the repository ends this change genuinely "editor-less" and "validate-first".

### C1 — Archive form
- **Chosen:** **git tag only, delete the files** (no `archive/` copy in the tree).

### C2 — CLI scope
- **Chosen:** **implement the minimal validation CLI this pass** — a
  `scripts/validate.mjs` (or thin package) that validates `data/` JSON against
  `core` schemas as the AI/agent entry point. No project generation / scaffolding.

### C3 — Remote branch deletion
- **Chosen:** **do not delete remote branches**; archive locally (tags) only.

### C4 — New development model
- **Chosen:** **module-scoped short-lived branches + validate-first workflow**:
  `main` long-lived stable; `feat/*` scoped to one module, merged-then-deleted;
  flow = AI generates JSON → CLI validate → tests → merge. Written into
  `docs/03-wal-process.md` and a new decision in `docs/02-open-questions.md`.
